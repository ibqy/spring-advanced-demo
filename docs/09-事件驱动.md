# 09 · 事件驱动机制

> ApplicationEvent + @TransactionalEventListener + 事件链 + 条件监听 + 幂等处理 —— 从基础到生产级的完整方案。

## 概述

Spring 的事件机制是框架内部实现模块解耦的核心手段。本 Demo 从基础的 `@EventListener` 出发，逐步深入到事务感知、事件链、条件过滤、自定义 Multicaster、幂等处理等生产级模式。

## 核心概念

### 事件驱动模型

```
┌──────────────┐     ┌──────────────────┐     ┌──────────────────┐
│  Publisher   │────▶│  EventMulticaster│────▶│  Listener A      │
│  (发布者)    │     │  (广播器,        │     │  @Order(1) 同步  │
└──────────────┘     │   异常隔离)      │     ├──────────────────┤
                     │                  │────▶│  Listener B      │
                     │                  │     │  @Async 异步     │
                     │                  │     ├──────────────────┤
                     │                  │────▶│  Listener C      │
                     │                  │     │  @Tx AFTER_COMMIT│
                     └──────────────────┘     └──────────────────┘
```

### 事件生命周期

| 阶段 | 说明 | 对应注解 |
|------|------|---------|
| 发布 | `ApplicationEventPublisher.publishEvent()` | — |
| 同步分发 | 在发布线程同步执行，阻塞发布者 | `@EventListener` |
| 条件过滤 | SpEL 表达式决定是否执行 | `@EventListener(condition=...)` |
| 异步分发 | 在虚拟线程池异步执行，不阻塞 | `@Async + @EventListener` |
| 事务感知 | 在事务提交/回滚后执行 | `@TransactionalEventListener` |

## 代码走读

### 1. 定义事件（Record 形式）

```java
// 不可变事件对象，Spring Boot 3.x+ 推荐用 record
public record OrderCreatedEvent(
    String orderId,
    double amount,
    String customer,
    LocalDateTime timestamp
) {
    public OrderCreatedEvent(String orderId, double amount, String customer) {
        this(orderId, amount, customer, LocalDateTime.now());
    }
}
```

### 2. 事件链模式（多阶段生命周期）

```
OrderCreatedEvent ──→ OrderPaidEvent ──→ OrderShippedEvent
     │                     │                    │
[记录审计日志]         [发送支付确认]        [发送物流通知]
[风控检查]            [更新库存]           [触发签收超时计时]
```

所有事件通过 `orderId`（correlationId）关联，形成完整的业务链路追踪。

### 3. 条件监听（SpEL 过滤）

```java
// 只有金额 > 500 才触发大额订单审核
@EventListener(condition = "#event.amount() > 500")
public void onHighValueOrderCreated(OrderCreatedEvent event) {
    log.warn("大额订单 {} 需要人工审核", event.orderId());
}

// 组合条件
@EventListener(condition = "#event.amount() > 1000 && #event.customer().startsWith('张')")
public void onSpecialCase(OrderCreatedEvent event) { ... }
```

**条件监听 vs 方法内 if 判断：**
- SpEL 条件不满足时方法根本不被调用（性能更好）
- 注解上直接看到过滤条件（可读性更好）
- 适合简单条件，复杂逻辑仍用方法内 if

### 4. 自定义 Multicaster（异常隔离）

```java
@Bean
public ApplicationEventMulticaster applicationEventMulticaster() {
    SimpleApplicationEventMulticaster multicaster = new SimpleApplicationEventMulticaster();

    // 关键：单个监听器异常不影响其他监听器
    multicaster.setErrorHandler(throwable ->
        log.error("监听器执行异常（已隔离）: {}", throwable.getMessage()));

    // 为 @Async 监听器配置虚拟线程池
    multicaster.setTaskExecutor(new VirtualThreadTaskExecutor("event-async-"));

    return multicaster;
}
```

### 5. 幂等处理（事件去重）

```java
// 用 Set 记录已处理的事件 ID
private final Set<String> processedIds = ConcurrentHashMap.newKeySet();

@EventListener
public void onOrderCreated(OrderCreatedEvent event) {
    if (!processedIds.add(event.orderId())) {
        log.warn("重复事件，跳过: {}", event.orderId());
        return;
    }
    // 正常处理逻辑...
}
```

生产环境用 Redis `SETNX` 实现分布式去重，设置 TTL 避免内存无限增长。

### 6. Spring 内置生命周期事件

```
ApplicationStartingEvent → ApplicationStartedEvent → ApplicationReadyEvent
                                                              ↓
                                                    ContextClosedEvent（关闭）
```

```java
// 方式一：实现 ApplicationListener 接口
@Component
public class MyListener implements ApplicationListener<ApplicationReadyEvent> {
    @Override
    public void onApplicationEvent(ApplicationReadyEvent event) {
        // 预热缓存、注册服务发现
    }
}

// 方式二：@EventListener 注解（一个类监听多种事件）
@EventListener
public void onContextClosed(ContextClosedEvent event) {
    // 优雅关闭：刷写缓冲区、释放连接
}
```

## 注解与 API 参考

| 注解 / API | 说明 |
|-----------|------|
| `ApplicationEvent` | 事件基类 |
| `ApplicationEventPublisher` | 事件发布器接口 |
| `@EventListener` | 标注事件监听方法 |
| `@EventListener(condition = "...")` | SpEL 条件过滤 |
| `@TransactionalEventListener` | 事务感知的事件监听 |
| `TransactionPhase.BEFORE_COMMIT` | 事务提交前触发（异常会导致回滚） |
| `TransactionPhase.AFTER_COMMIT` | 事务提交后触发（最常用） |
| `TransactionPhase.AFTER_ROLLBACK` | 事务回滚后触发 |
| `TransactionPhase.AFTER_COMPLETION` | 事务完成后触发（无论提交/回滚） |
| `@Async` | 异步执行事件监听 |
| `@Order` | 控制监听器执行顺序 |
| `ApplicationEventMulticaster` | 事件广播器（可自定义异常隔离策略） |

## 面试考点

::: warning 高频面试题
1. **@EventListener 和 @TransactionalEventListener 的区别？**
   - `@EventListener`：事件发布时立即执行（事务未提交）
   - `@TransactionalEventListener`：事务提交/回滚后才执行
   - 使用场景：发送通知用 `@EventListener`，需要确保数据已持久化用 `@TransactionalEventListener`

2. **事件是同步还是异步的？**
   - 默认同步：在发布线程执行
   - `@Async` + `@EventListener`：异步执行
   - Spring Boot 4.1 启用虚拟线程后，异步事件使用虚拟线程

3. **如何处理事件监听异常？**
   - 同步监听器异常会传播到发布者，可能导致事务回滚
   - 自定义 `ApplicationEventMulticaster` 的 `ErrorHandler` 实现异常隔离
   - 或使用 `@Async` 异步隔离

4. **事件链 vs 状态机？**
   - 事件链更松耦合，每个监听器只关心自己的阶段
   - 状态机是集中式的，流程可视化更好
   - 用 correlationId（orderId）串联事件链
:::

## 常见陷阱

::: danger 陷阱 1：@EventListener 中查询未提交数据
`@EventListener` 在事务提交前执行，此时查询数据库可能查不到刚插入的数据。应该用 `@TransactionalEventListener(phase = AFTER_COMMIT)`。
:::

::: danger 陷阱 2：同步监听器阻塞主流程
耗时操作（发邮件、调用外部 API）放在同步 `@EventListener` 中会阻塞主请求。应使用 `@Async` 或消息队列。
:::

::: danger 陷阱 3：事件丢失
Spring 事件是内存级别的，进程崩溃则丢失。重要业务事件应使用持久化消息（数据库 + 消息队列）。
:::

::: danger 陷阱 4：一个监听器异常导致全部失败
默认的 `SimpleApplicationEventMulticaster` 不做异常隔离。一个监听器抛异常，后续监听器全部跳过。生产环境必须自定义 `ErrorHandler`。
:::

::: danger 陷阱 5：重复事件导致数据不一致
消息队列重试、网络重发等场景会导致同一事件被处理多次。关键业务操作（扣库存、发积分）必须实现幂等。
:::
